# 文件审计标准

本文件定义文件审计（场景三）使用的8个审计维度。文件审计不跑流程，只检查工作流文件本身的规则定义是否完备、一致、无冲突。

---

## 严重度定义

同体验审计标准：S1（轻微）、S2（中等）、S3（严重）。

## 记录格式

```
[维度]：（8个维度之一）
[严重度]：S1/S2/S3
[问题]：具体描述
[定位]：文件名 → 章节 → 具体位置
[建议]：具体修改内容
```

---

## 维度一：节点职责清晰度

**定义**：每个Skill是否只做一件事，职责边界是否明确，有没有重叠或真空。

**检查要点**：
1. 每个Skill的职责描述是否用一句话说得清
2. 是否存在两个Skill做类似的事（职责重叠）
3. 是否存在某些任务没有任何Skill负责（职责真空）
4. Skill内部的步骤是否都服务于该Skill的核心职责（没有越界）

**判定标准**：
- 通过：每个Skill职责单一明确，无重叠无真空
- S1：个别步骤的归属有轻微模糊，但不影响执行
- S2：有2个Skill的职责有明显重叠，或存在1个明确的职责真空
- S3：多个Skill职责混乱，执行时不知道该用哪个

**典型问题示例**：
1. Skill C（品牌调性）和 Skill D（方案生成）都在做"设计方向定义"，边界不清
2. "客户沟通话术准备"这个任务在A-H中没有任何Skill负责

---

## 维度二：输入输出契约

**定义**：每个Skill的输入要求和输出格式是否被明确定义，上下游节点能否无缝对接。

**检查要点**：
1. 每个Skill是否明确定义了"我需要什么输入"
2. 每个Skill是否明确定义了"我输出什么格式"
3. 上游Skill的输出格式是否匹配下游Skill的输入要求
4. 可选输入和必选输入是否区分清楚

**判定标准**：
- 通过：每个Skill的输入输出都有明确的格式定义，上下游可无缝对接
- S1：输入输出有定义但不够精确（如"提供项目信息"没有列出具体字段）
- S2：上游输出和下游输入存在格式不匹配，需要人工转换
- S3：某个Skill的输入完全没有定义，执行时只能靠猜

**典型问题示例**：
1. Skill A 输出的"项目简报"没有定义包含哪些字段，Skill B 不知道该读取什么
2. Skill D 需要的"品牌约束"格式和 Skill C 输出的"品牌调性定义"格式不一致

---

## 维度三：决策点合理性

**定义**：工作流中需要用户做决策的地方，选项是否清晰，有没有可以被规则化从而省去的。

**检查要点**：
1. 每个决策点的选项是否互斥且完整（没有遗漏选项，没有重叠选项）
2. 选项的描述是否足够让用户做出判断
3. 是否存在可以由系统自动决定的决策点（用规则替代人工判断）
4. 决策结果如何影响后续流程是否有明确说明

**判定标准**：
- 通过：决策点清晰，选项完整互斥，需要人工的确实需要人工
- S1：选项描述可以更清晰，但不影响决策
- S2：存在1-2个可以规则化的决策点，浪费用户时间
- S3：决策选项模糊不清，用户无法做出有意义的选择

**典型问题示例**：
1. Skill B 让用户选"匹配模式"（精确/模糊/自动），但80%的场景下"自动"都是最优选择，这个决策点可以规则化
2. 方案评审时给出"通过/修改/淘汰"三个选项，但没说明"修改"后流程怎么走

---

## 维度四：信息传递完整性

**定义**：关键信息从Skill A到Skill H的传递链路是否完整，有没有信息在中间节点丢失。

**检查要点**：
1. 用户在Skill A输入的核心约束（预算、市场、品牌、使用场景），在后续每个Skill中是否被引用
2. 每个Skill是否明确声明它从上游接收哪些信息
3. 信息传递是否有显式的载体（状态卡、项目简报等），还是靠隐式的上下文记忆
4. 当某个Skill修改了上游信息时，下游是否会被通知

**判定标准**：
- 通过：核心约束从A到H全程可追溯，传递载体明确
- S1：非核心信息传递依赖隐式上下文，但核心约束传递完整
- S2：有1-2个核心约束的传递链断裂，需要用户在中间节点手动补充
- S3：信息传递完全依赖上下文记忆，没有显式载体，丢信息是必然的

**典型问题示例**：
1. 预算约束在Skill A的状态卡中定义，但Skill D的方案生成规则中没有引用预算字段
2. Skill C 定义的品牌色彩约束没有传递到 Skill E 的CMF方案中

---

## 维度五：规则冲突与冗余

**定义**：不同文件、不同Skill之间的规则是否存在矛盾或不必要的重复。

**检查要点**：
1. Instructions 中的全局规则和各Skill的局部规则是否一致
2. 不同Skill中对同一概念的定义是否一致（如"方案完成标准"）
3. 是否有规则在多个文件中重复定义（维护时容易不同步）
4. 条件判断是否存在逻辑矛盾（同一条件走向不同结果）

**判定标准**：
- 通过：规则无矛盾，无不必要重复，定义一致
- S1：有少量重复定义但内容一致，暂时不影响
- S2：有规则冲突但发生在低频场景，大部分时候不会触发
- S3：关键规则冲突，执行时必然出现矛盾结果

**典型问题示例**：
1. Instructions说"方案数量不少于10个"，Skill D说"输出8-12个方案"，边界不一致
2. Skill F和Skill G都定义了"客户提案格式"，但字段不同

---

## 维度六：失败回退路径

**定义**：当某个环节失败或输出不达标时，是否有明确的回退规则。

**检查要点**：
1. 每个Skill是否定义了"什么情况算失败"
2. 失败后是否有明确的回退目标（退回哪个Skill、重做哪个步骤）
3. 回退后是否会导致信息丢失
4. 是否存在死循环风险（A退回B，B退回A）
5. 最大重试次数是否有限制

**判定标准**：
- 通过：每个Skill有明确的失败条件和回退路径，无死循环风险
- S1：失败条件定义了但回退路径不够细（"退回上一步"但没说具体退到哪）
- S2：部分Skill没有定义失败回退，失败时只能从头开始
- S3：存在死循环回退路径，或失败后没有任何处理规则

**典型问题示例**：
1. Skill D方案评审全部淘汰后，规则只说"重新生成"，没说保留哪些约束、改变哪些参数
2. Skill B客户匹配失败后退回Skill A，Skill A又因为同样的输入走到Skill B，形成死循环

---

## 维度七：品类泛化能力

**定义**：工作流规则切换到不同品类时，哪些节点会跑不通。

**检查要点**：
1. 规则中是否存在硬编码的品类特有逻辑（如"灯具必须考虑光学"写死在通用流程中）
2. 品类特有的知识是否和通用流程逻辑分离
3. 换到非灯具品类（如家具、工具、电子产品）时，每个Skill是否仍可执行
4. 品类相关的评判标准是否可配置（而不是写死在Skill中）

**判定标准**：
- 通过：品类特有逻辑和通用流程分离，换品类只需更换品类配置
- S1：个别Skill中有品类特有表述，但不影响其他品类执行
- S2：有2-3个Skill强绑定灯具逻辑，换品类需要修改Skill内容
- S3：核心流程逻辑强依赖灯具品类，换品类基本跑不通

**典型问题示例**：
1. Skill D的方案评审标准中写死了"光效≥100lm/W"作为通过条件，非灯具品类无法适用
2. Skill E的CMF方案模板强制要求"透镜材料"字段，非灯具品类不需要

---

## 维度八：自动化可行性

**定义**：哪些当前需要人工介入的步骤可以被规则化，从而提升效率。

**检查要点**：
1. 哪些用户确认步骤可以用规则自动判定（如"如果客户档案中品牌调性已定义，自动跳过调性确认"）
2. 哪些信息查找可以自动化（如"自动从客户档案读取历史项目偏好"）
3. 哪些格式转换可以脚本化（如"自动将内部方案格式转为客户提案格式"）
4. 自动化后是否影响用户的控制感（有些地方人工介入是必要的）

**判定标准**：
- 通过：当前所有人工介入都是必要的，没有可以规则化的步骤
- S1：有1-2个低风险步骤可以自动化，但当前方式也能接受
- S2：有3个以上步骤可以自动化，当前人工介入明显影响效率
- S3：大量不必要的人工介入，工作流效率严重受限

**典型问题示例**：
1. 每次跑流程都要手动确认"是否使用该客户档案"，当用户已经指定客户名时这步完全多余
2. Skill G 输出后需要手动复制粘贴到客户提案模板，这个格式转换可以自动完成
