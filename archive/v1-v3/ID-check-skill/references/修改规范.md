# 修改规范

本文件定义审计发现问题后的修改流程和规范。核心原则：每次修改都精准、可控、可追溯。

---

## 修改原则

### 最小改动
只改导致问题的位置，不顺手重构周边代码。发现旁边的规则也可以优化？记下来，下次再说。改一个地方就够了。

### 一次一处
每条修改建议只解决一个问题。不要把两个不相关的修改合并到一条建议里，即使它们在同一个文件中。用户需要能对每个修改独立做出判断。

### 可回滚
修改前必须记录原文。写入审计日志时，原文和修改后的内容都要完整保存。出了问题能退回去。

### 改完说明
每次修改执行后，立刻写入 `audit_log.md`。不是做完所有修改再统一写，而是每条确认执行后立刻写。

---

## 修改建议输出格式

每条修改建议必须包含以下7个字段，缺一不可：

```
[问题ID]：AUD-YYYYMMDD-NNN（如 AUD-20260401-001）
[文件]：具体文件名（如 claude-project/Skill-D-方案生成.md）
[位置]：文件中的具体章节/行（如 "## 方案评审标准 > 第3条"）
[当前内容]：
目前写的是什么（原文引用，保持原始格式）

[修改为]：
改成什么（给出完整的可替换内容，可以直接复制粘贴替换原文）

[原因]：为什么要改（用一句话说清楚，关联到审计维度和严重度）
[预期效果]：改完后预期会怎样（具体到用户体验或输出质量的变化）
```

### 格式要求

- **[当前内容]** 和 **[修改为]** 必须是完整的、可直接替换的文本块，不是"把XX改成YY"这种指示
- 如果是新增内容（不是替换），[当前内容] 写"（新增，在XXX之后插入）"
- 如果是删除内容，[修改为] 写"（删除此段）"
- 引用原文时保持原始缩进和格式

---

## 禁止行为

以下行为严格禁止：

1. **未经用户确认直接修改文件**——任何情况下都不行，即使你觉得改动很小很安全
2. **一次改多个不相关问题**——每条建议只解决一个问题
3. **修改时顺手优化其他部分**——发现旁边可以优化的，记下来，不要现在动
4. **给出抽象建议而不是具体修改内容**——"建议优化此处的表述"是废话，要给出具体改成什么

---

## 用户确认交互方式

修改建议逐条展示，用户对每条做出以下三种回复之一：

| 回复 | 含义 | 后续动作 |
|------|------|---------|
| **接受** / **Y** / **好** | 同意修改 | 立刻执行修改，写入审计日志 |
| **拒绝** / **N** / **不改** | 不同意修改 | 跳过，在审计日志中记录为"用户拒绝"，保留问题记录 |
| **改一下** + 用户的修改意见 | 有条件接受 | 根据用户意见调整修改内容，再次展示确认后执行 |

### 交互规则

- 一次展示一条，不要批量丢给用户
- 展示时先说问题是什么、为什么要改，再给修改内容
- 用户说"全部接受"时，可以批量执行，但每条仍需写入审计日志
- 用户说"先看完再说"时，全部展示完毕后再逐条确认

---

## 审计日志写入格式

每条修改执行后，按以下格式追加到 `audit_log.md` 的记录区：

```
### AUD-YYYYMMDD-NNN

- **日期**：YYYY-MM-DD
- **场景**：模拟审计 / 事后审计 / 文件审计
- **Brief**：（如有）B01_便携工作灯_ACG
- **节点**：Skill X - Step Y
- **维度**：XXX
- **严重度**：S1/S2/S3
- **问题**：具体描述
- **定位**：文件名 → 章节 → 位置
- **状态**：已修复 / 用户拒绝 / 待修复
- **修改前**：原文
- **修改后**：新内容（如状态为已修复）
```

同时更新统计区的数字。

---

## 版本迭代规则

审计修改完成后，被修改的文件必须迭代版本号。这是硬规则，不可跳过。

### 执行时机

**所有修改建议逐条确认并执行完毕后**，统一做一次版本迭代（不是每条修改都迭代一次）。

### 操作步骤

1. **识别被修改的文件**：汇总本次审计中实际执行了修改的文件列表
2. **提取当前版本号**：从文件名中提取 `_vN` 后缀（如 `技能A-H_v19.md` → 19）
3. **版本号+1**：重命名文件（如 `技能A-H_v19.md` → `技能A-H_v20.md`）
4. **更新引用**：在其他工作流文件中搜索旧文件名，替换为新文件名。需要检查的位置：
   - `Instructions` 中的"读取文件的规则"章节（第十一条）
   - `SKILL.md` 和 references 中的文件引用
   - 任何其他引用了旧文件名的地方
5. **告知用户**：输出版本迭代摘要，格式：
   ```
   ────────────────────
   📦 版本迭代
   - 技能A-H_v19.md → 技能A-H_v20.md
   - Instructions_v17.md → Instructions_v18.md
   引用已同步更新：[列出更新了引用的文件]
   ────────────────────
   ```

### 注意事项

- 只有实际被修改的文件才迭代版本号，未修改的文件保持原版本
- 如果文件名中没有 `_vN` 后缀，不做重命名，但在审计日志中记录"该文件无版本号后缀"
- 版本迭代本身不需要用户逐条确认（修改已经确认过了），但需要在摘要中告知用户

---

## 复发处理

如果审计日志中某个问题之前标记为"已修复"，但在新一次审计中再次出现：

1. 标记为"复发"
2. 严重度自动提升一级（S1→S2，S2→S3，S3保持S3）
3. 在新记录中引用原问题ID
4. 分析复发原因——是修改不到位，还是上游又产生了同样的问题
