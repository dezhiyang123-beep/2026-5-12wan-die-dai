# hypothesis-check — 假设管理SOP

## 事实/推断/假设分层标准

| 等级 | 定义 | 标注格式 |
|------|------|---------|
| `[H]` 事实 | 有可追溯来源（URL/规范号/客户文件/竞品链接）| `陈述[H-来源]` |
| `[M]` 推断 | 有合理类比但无直接可追溯证据 | `陈述[M-类比说明]` |
| `[L]` 假设 | 纯推测或关键参数缺失 | `陈述[L-待验证]` |

**禁止虚标规则：**
- 关键字段（价格/规格/认证/用户行为）不得用推测标为[H]
- 已验证假设 ≠ 事实：即使通过了一次验证，来源不可追溯的仍为[M]

## 已验证 vs 待验证假设区分

**已验证假设：**
- 有明确验证动作的记录
- 验证结果支持假设
- 来源标注[H]或[M]

**待验证假设：**
- 当前无证据支撑
- 必须标[L]
- 必须附验证动作模板

## 反论据生成要求

每条设计方向必须有≥1条反论据。反论据生成步骤：
1. 找到该方向的核心假设（通常是"用户需要X"或"市场缺少Y"）
2. 质疑：这个假设如果错了，会怎样？
3. 找到已有证据中与假设矛盾的数据
4. 输出格式：
   ```
   反论据：[具体陈述，必须有来源标注]
   影响：如果成立，[该方向会怎样]
   ```

反论据禁止：
- "可能会有风险"（太泛）
- "竞品也在做"（不是反论据，是证据）
- 无来源标注的陈述

## 验证动作模板

每个待验证假设[L]必须附：
```
验证方式：[具体可执行动作，如"搜索amazon.com该品类前10 SKU价格分布"]
预计耗时：[10分钟内/1小时内/需要联系客户]
验证标准：[什么结果视为假设成立]
```

## 交付物中的假设处理规则

- [L]假设不得直接出现在任何交付物正文（PPT/PRD）
- 处理方式二选一：
  - 补证据升级为[M]或[H]后写入正文
  - 改为"待验证假设"格式，移至备注/附录，正文用[UNKNOWN]占位
- analyst_pick中引用的证据不得为[L]（分析师建议必须基于[H]或[M]证据）
