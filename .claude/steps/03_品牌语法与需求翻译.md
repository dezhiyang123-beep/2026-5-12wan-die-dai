# Step 03：品牌语法建模 + 需求翻译

## 目标
1. 建立品牌语法（不只是"长什么样"，而是"为什么这样长，怎么变仍然像它"）
2. 三层需求分析 + 造型意图翻译（含三重校验）
3. 3个设计方向

## 输入
- Step 01 品类扫描报告
- Step 01 反面证据（counter_evidence CE-01~03）
- Step 02 品类骨架
- 品类设计谱系图（Step 02产出，或已有）
- 客户名称

## 【R3强制】上游约束Status复核

执行品牌语法建模前，复核Step 01-02传入的所有约束：

| 约束描述 | 来源步骤 | 原status | 证据等级 | 本步使用权限 |
|---------|---------|---------|---------|------------|
| （从Step 01/02产出中逐条填写） | | | | HARD/SOFT/EXPLORE_ONLY |

INFERENCE/HYPOTHESIS来源的约束在本步骤只能作"软引用"——不能作为方向淘汰依据，只能作为风险提示。

**【R3强化】约束引用时刻检查点**：在品牌语法提取、需求分析、方向制定的任何分析文本中，每次引用来自Step 01/02的约束，必须在当前句后括注其status等级，格式：`（status: FACT/INFERENCE, 来源：Step 0X）`。不允许裸用约束（即引用约束但不标注status）——裸用视同将INFERENCE当FACT使用。

- F25未通过的方向不能作为候选方向呈现给用户

## 任务一：品牌语法建模

### 第一步：品牌产品图采集

**优先使用02_品牌语法库中已有的客户品牌图片**。如果02中已有该品牌≥15张图（按current_line/premium_series/detail_views分类），直接使用，不需要重新搜索。如果不足15张，从客户官网补充采集至≥15张。

**【R7】零图片处理路径**（品牌语法库完全为空时）：

| 品牌图片数量 | 状态 | 处理方式 |
|------------|------|---------|
| ≥15张 | 正常 | 直接提取5码 |
| 5-14张 | 受限 | 提取5码但标注 LOW_CONFIDENCE，C/D级比例预计偏高，用户确认后继续 |
| 1-4张 | 严重不足 | 从官网手动采集后继续，或标注"品牌语法提取置信度极低（evidence_level D为主）"，用户选择是否继续 |
| 0张 | 停机 | 必须先补充品牌图片。路径：用户提供品牌官网URL → AI提取10+张代表产品描述 → 生成知识参照卡（知识参照卡不算15张图，但可作为5码提取的辅助依据） |

无论哪种情况，5码提取后的证据等级标注必须真实反映图片数量——图片少→更多C/D级，不能伪造A/B级证据。

### 第二步：5码提取

系统读图自动提取品牌语法5码：

```yaml
brand_grammar:
  surface_codes:          # 表面码（准确度最高）
    color_logic: ""       # 不只是"黄+黑"，而是"黄色用在哪、黑色用在哪、为什么这么分"
    material_zones: ""    # 哪里用金属、哪里用塑料、哪里用橡胶
    finish: ""            # 主要表面处理

  proportion_codes:       # 比例码（中等准确度，需确认）
    volume_distribution: "" # 各功能区的体量关系
    visual_weight_center: "" # 视觉重心位置
    line_tension: ""       # 线条风格（硬朗直线/流畅曲线/混合）

  structure_codes:        # 结构码（中等准确度，需确认）
    parting_style: ""     # 分件方式
    overmold_style: ""    # 包胶/软硬结合方式
    opening_style: ""     # 开孔/散热口风格
    fastener_visibility: "" # 螺丝/卡扣是否外露

  semantic_codes:         # 语义码（容易泛化，需证据）
    brand_personality: "" # 品牌传递的性格
    user_expectation: ""  # 用户对品牌的期待
    power_source: ""      # 力量感/亲和感/专业感从哪来

  forbidden_codes:        # 禁止码（最容易出错，必须用户确认）
    forbidden_forms: []   # 绝对不能出现的造型
    forbidden_competitors: [] # 不能靠近的竞品风格
    forbidden_semantics: [] # 不能使用的视觉语义
```

### 第三步：证据等级标注

**每条语法必须标注证据等级**：

| 等级 | 含义 | 使用权限 |
|------|------|----------|
| A | 15张产品图中≥12张一致 | 可作为硬约束 |
| B | 同系列产品一致（≥5张） | 可作为设计依据 |
| C | AI推断，无充分图片证据 | 可参考，不能做淘汰依据 |
| D | 用户经验判断 | 同C |

```yaml
grammar_item:
  claim: "黄色主要用于功能识别区（电池包、护罩），不是装饰色"
  evidence_level: "A"
  evidence: "15张产品图中14张一致"
  confidence: high
```

**C/D级不能单独作为淘汰概念的依据。**

### 第四步：用户确认（选择题模式）

不问开放问题。给选择题：

```
品牌语法已提取。请确认：

1. 该品牌的整体性格最接近：
   A. 专业强悍（如DeWalt/Milwaukee）
   B. 家用亲和（如Ryobi/Black+Decker）
   C. 科技极简（如Dyson/Apple）
   D. 其他：____

2. 该品牌绝对不能做的是：
   A. 圆润可爱的消费品曲面
   B. 极简光滑的科技产品风
   C. 以上都不能做
   D. 其实都可以尝试

3. 该品牌的黄色（或主品牌色）主要用于：
   A. 功能分区（电池/护罩/标识区）
   B. 整体装饰
   C. 不确定
   
...
```

**确认时间预估**：3-5个选择题，1-2分钟完成。

## 任务二：三层需求分析

### 第1层：客户显性需求
从brief直接提取，置信度 HIGH。

### 第2层：客户隐性需求
从市场数据异常、产品线缺口推断，每条附证据，等用户确认。

### 第3层：消费者行为层痛点
从用户评论/竞品差评/论坛提取行为层面的痛苦。所有痛点编号为PP-01、PP-02……

**【R12】痛点全覆盖要求**：
- F19 需求翻译必须覆盖**所有**识别出的PP-XX痛点，不只是前3名
- 每个PP-XX必须映射到至少一个造型策略，或明确标注"本项目方向不回应此痛点，原因：___"
- 3个方向对比表中，必须列出每个方向回应了哪些PP-XX，未回应哪些
- Step 05 5方案角色分配时，必须检查全部PP-XX是否有概念回应

---

## 任务三：需求→造型意图翻译（含三重校验）

对排名前3的消费者痛点，各翻译为造型策略。

每条策略必须通过三重校验：
1. **证据支撑**：有没有证据表明用户真有这个痛点？
2. **反例检查**：有没有相反的可能？
3. **用户可理解性**：目标用户看到造型能自发理解吗？

不通过的策略降级或重新翻译。

---

## 任务四：3个设计方向

每个方向必须包含：
- 回应的核心痛点（链接任务三）
- 造型意图（链接任务三翻译表）
- 在品类谱系图上的位置
- 老板7维度预评
- 购买句雏形："这款产品比普通产品更____"
- 对应的反面证据回应（Step 01的counter_evidence中哪些风险和这个方向相关？如何应对？）
- **【R13】致命依赖识别**：
  ```yaml
  fatal_dependencies:
    - dependency: ""          # Hero Feature依赖的外部条件（如"依赖第三方API开放"）
      validation_step: ""     # 应在哪步验证（Step 03/04/05）
      if_not_validated: ""    # 无法验证时的备选方案
      validated: true/false   # 本步骤内是否已能验证
  ```
  致命依赖必须在用户选方向之前明确列出。用户选的方向有未验证的致命依赖→必须告知风险。

用户选择1个方向。

## 输出
1. 品牌语法5码（含证据等级）→ 选择题确认
2. 三层需求分析表
3. 造型意图翻译表（含三重校验）→ 等用户确认
4. 3个方向对比表 → 等用户选择
5. 品牌语法（含品牌红线表/绿灯表，来自F01）存入 `.claude/clients/{客户名}/brand_grammar.yaml`

### 客户记忆写入规则（防覆盖）

**brand_grammar.yaml**：
- 首次创建：直接写入
- 已存在时：不覆盖旧版。在文件头部追加新版本块，保留历史版本：
```yaml
# === V2 (2026-05-11, 项目RAB-002) ===
# 更新原因: 确认黄色不用于功能分区（V1误判）
brand_grammar_v2:
  ...

# === V1 (2026-05-11, 项目RAB-001) ===  
brand_grammar_v1:
  ...
```
- 每个版本块标注：版本号、日期、项目ID、更新原因
- 最新版本在最上面，系统读取时取最上面的版本块

**preferences.yaml**：
- 同上规则，追加不覆盖，每次更新标注日期和原因
