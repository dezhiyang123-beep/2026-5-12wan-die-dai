# Step 04：迁移型灵感验证

## 目标
不是寻找好看的参考图，而是寻找能够回应当前消费者痛点、符合客户品牌红线、并可转化为当前品类造型策略的**可迁移设计机制**。

## 输入
- Step 03 确认的消费者痛点 + 造型策略（**用户选定方向**）
- Step 03 品牌红线表/绿灯表
- Step 01 成本走廊
- Step 01 认证/结构限制
- 目标客户渠道与价格带
- 视觉素材库 + 反例库

**【R19】用户方向选择的执行强度**：

用户在Step 03选定了某一方向（如D3），意味着：
- **D3（选定方向）**：主线方向，Step 04所有迁移检索的第一优先级，5方案至少3个必须来自D3策略体系
- **D1/D2（淘汰方向）**：仅允许作为"同品类参照来源"使用，必须明确标注 `reference_only: true`。淘汰方向的造型策略不能复活为正式方向——如需引用D1/D2的参照产品，格式为"参照D1中的XXX元素作为对比，非设计主线"
- 如果Step 04发现D3方向素材严重不足（同品类DNA=0且用户选B降级），可引入D1/D2的部分策略，但必须在确认检查点明确告知用户"D3素材不足，已引入D2的XXX元素，请确认"

## 【R3强制】上游约束Status复核

执行04A前，复核所有传入约束的Status：

```yaml
upstream_status_review:
  hard_constraints: []    # FACT(A/B级)来源的约束，可直接限制设计
  soft_constraints: []    # INFERENCE来源的约束，仅作参考，不能作为迁移FAIL理由
  invalidated: []         # HYPOTHESIS/NEEDS_VALIDATION来源的约束，本步骤不使用
```

INFERENCE来源的约束不能作为迁移合法性验证中的FAIL依据。只有FACT约束才能硬性拒绝灵感。

|------|------|---------|----------|

## 04B 跨品类方向推理

每条造型策略先转译为"抽象设计挑战"：

```yaml
strategy_id: "S-01"
pain_point: "灯太重，两个人才能装"
design_challenge: "在保持结构强度的前提下实现极致轻量化"
user_visible_signal: "用户拿在手里/看到产品时，能立刻感知'轻'"
success_test: "不懂产品的人看到造型3秒内能说出'thin/light/slim'"
forbidden_direction: "不能做成塑料感/廉价感来实现轻（违反品牌DNA）"
```

然后推理跨品类方向。**每个方向必须通过3项校验**：

| 校验项 | 内容 | 不通过的后果 |
|--------|------|-------------|
| 约束相似 | 力学/人机/散热/安装压力是否相似？ | 1-5分 |
| 触点相似 | 用户接触方式是否相似？ | 1-5分 |
| 语义相似 | 借来的细节传达相同价值吗？ | 1-5分 |
| 制造相似 | 目标品类能用可接受工艺实现吗？ | 1-5分 |

**量化评分规则**：
- 单项 < 3分 → 禁止迁移
- 总分 < 14分（满分20）→ 禁止迁移
- 总分 ≥ 16分 → 可检索
- 总分 14-15分 → 低置信检索（该方向最多贡献1个概念）

```yaml
cross_category_targets:
  - category: "笔记本电脑"
    benchmark_products: ["MacBook Air", "Dell XPS 13"]
    pressure_similar: true   # 消费者把薄轻作为核心购买理由
    constraint_similar: true # 铝合金壳体+散热约束，和灯具相似
    perception_similar: true # 用户看到薄就觉得轻，感知一致
    score: 3  # 可检索
    what_to_look_for: "楔形截面、一体化铝壳、接口集中处理"
```

## 04C 素材库检索

### 检索前：检查素材库覆盖

检查04B推理出的品类在素材库中的覆盖情况。不足时的处理：

| 命中量 | 状态 | 处理 |
|--------|------|------|
| ≥ 3张 | 可用 | 正常检索 |
| 2张 | 勉强可用 | 只允许生成安全概念或局部细节概念 |
| 1张 | 低置信 | 可补1张知识参照卡，但该策略最多生成1个概念 |
| 0张 | 不可用 | **见【R7】零覆盖处理路径** |

**【R7】零覆盖（同品类DNA=0）处理路径**（禁止自决放行）：

步骤1：确认索引 vs 实际 — 先检查素材索引文件是否存在但路径损坏。如有路径错误 → 修复路径后重新检索。

步骤2：告知用户 — 如确认素材库无此品类，必须明确告知：
```
"素材库中目前无{品类}同品类产品图片。有三条路可走：
A. 用户补充素材（路径：~/Desktop/设计素材库/01_品类标杆库/{品类}/），约等待10-15分钟处理
B. 用降级方案继续：主骨架改用知识参照卡（evidence_level D），最终5方案中知识参照卡主导的概念不超过2个，且不能做冠军款
C. 停机，等素材补充后继续"
```

步骤3：等用户选择后执行，禁止自决放行继续流程。

**反例库为空时的处理**：基于Step 02的常见失败造型 + 品牌禁止码生成临时反例卡，标注 `source: "generated_from_step02"` + `needs_real_example: true`。项目结束Step 10时经用户确认正式入库或删除。

**不自动用知识参照卡填满空位。** 宁可少生成概念，也不让低质量灵感占名额。

### 素材库检索强制覆盖规则

检索时必须覆盖以下所有来源，不允许只看单一品牌：

1. **同品类标杆**：从01_品类标杆库中，至少检索3个不同品牌的DNA卡
2. **客户自身**：如果客户品牌在01中有图，必须检索客户现有产品作为基线对比
3. **跨品类手法**：从03_设计手法库中，按造型策略匹配的手法检索（不限品类）
4. **反例库**：从04_失败反例库中检索，每条策略至少1张反例

**检索query多样性**：每条造型策略至少用3个不同角度的检索query（按problem_solved、按手法标签、按品类），避免只用一个query导致结果同质化。

检索结果去重后，最终灵感锁定表中：
- 同品类参照 ≥ 3张（来自≥2个品牌）
- 跨品类参照 ≥ 2张
- 反例 ≥ 3张（每条策略1张）

不满足 → 补充检索后再输出灵感锁定表。

### 三类检索

**1. 产品级参照**（借整体比例/轮廓/Hero Feature表达）
- 按 problem_solved → silhouette + hero_feature → transferable_technique 优先级检索
- 不限品类，全库搜索

**2. 细节级参照**（借线条/转角/分缝/材质过渡/结构暗示）
- 检索 DNA 卡的 extractable_details 字段
- 用标签高效检索（见下方标签体系）

**3. 反例参照**（什么不能学）
- 从反例库 `.claude/knowledge/反例库/` 中检索
- 每条策略应输出至少1张反例卡（从反例库检索，或基于品类常见失败模式生成临时反例）
- **反例库为空时**：基于 Step 02 常见失败造型 + 品牌禁止码生成临时反例卡，标注 `source: "generated"`，项目结束后经用户确认入库

### 细节检索标签体系

DNA卡的 extractable_details 必须包含以下标签字段，用于高效检索：

```yaml
detail_type:     # line / edge / seam / proportion / texture / grille / handle / joint / transition / display / light_effect
transfer_value:  # lightweight / premium / rugged / friendly / technical / easy_install / slim / modular / low_glare / hidden_hardware
brand_fit:       # conservative / premium / playful / industrial / architectural / minimal
```

检索时组合标签查询，如：`transfer_value=lightweight + brand_fit=industrial + detail_type=seam`

### 检索后必须看原图

找到DNA卡后，不能只读DNA卡的文字描述就做决策。必须打开原图验证：
1. DNA卡的描述是否准确（silhouette、hero_feature和实际图片是否一致）
2. 图片中是否有DNA卡遗漏的可迁移细节
3. 图片的实际设计水平是否和DNA卡的design_level评分一致

只有原图验证通过的灵感才能进入04E迁移合法性验证。

### 检索过滤规则
- **排除 `needs_human_review: true` 的记录**：标记为待审核的产品不参与检索
- **排除缺少关键检索字段（product_name、silhouette、hero_feature）的记录**

### 路径B：视觉驱动发现

从素材库中抽取15-20张图浏览，**强制品类配额**：

```
同品类（如灯具）：最多3张
消费电子：3张
汽车/交通：3张
医疗/工具/户外：3张
家具/建筑/包装：3张
```

如果某品类素材不足，从跨品类冷启动包中补充（见素材库规范）。

对每张图扫描 extractable_details，问："这个细节和当前痛点有没有意外关联？"

## 04D 知识参照卡规则

知识参照卡**只能在素材库不足时使用**，且有严格限制：

```yaml
knowledge_reference_rules:
  allowed:
    - 定性描述（"楔形截面，前薄后厚"）
    - 造型趋势（"消费电子普遍追求一体化无缝"）
    - 结构逻辑（"接口集中在最厚处，薄处做纯视觉面"）
    - 用户感知（"楔形让人觉得比实际更薄"）
    - 可迁移方向（"楔形截面逻辑可迁移到长条形灯具"）
  
  forbidden:
    - 具体尺寸（"前端3.5mm"）
    - 具体厚度/重量
    - 精确材料牌号
    - 精确成本
    - 具体认证参数
    - 未验证的品牌产品结构细节
  
  usage_permission:
    - 可用于启发和搜索方向
    - 不可作为硬约束
    - 不可作为Step 07渲染主参考
    - 不可单独支撑一个最终概念
    - 最终5方案中知识参照卡主导的概念不超过1个
```

**一句话：知识参照卡只能当"找图线索"，不能当"设计证据"。**

## 04E 迁移合法性验证（核心闸门）

**每个灵感（产品级+细节级）进入Step 05前，必须通过以下7项验证：**

```yaml
migration_validation:
  1_what_borrowed: ""      # 借的到底是什么？（轮廓/比例/细节/材质过渡/使用动作/结构表达）
  2_why_transferable: ""   # 为什么能迁移到当前产品？
  3_user_comprehension: "" # 迁移后用户能不能3秒理解？
  4_brand_compliance: ""   # 会不会违反品牌红线？
  5_cost_impact: ""        # 会不会超出成本走廊？
  6_manufacturing: ""      # 会不会制造困难？
  7_resemblance_risk: ""   # 会不会像抄袭某个标志性产品？
  
  result: "PASS / FAIL"   # 2项以上回答不清楚 → FAIL
```

**FAIL的灵感直接淘汰，不进入Step 05。**

## 04F 使用场景建模

**每个设计方向必须映射完整用户旅程，识别约束造型的物理交互。**

此部分直接为 Step 05 概念生成提供造型约束输入。

### 用户旅程6阶段

每个方向按以下阶段逐一分析：

```yaml
usage_scenario:
  strategy_id: "S-01"
  
  1_unbox:
    who: ""                # 谁拆箱？终端用户/安装工/仓库人员？
    actions: []            # 物理动作：拆、抽、翻、提
    form_constraints: []   # 对造型的约束（如：必须有明确的提手位/抓握面）
    
  2_install:
    who: ""                # 谁安装？怎么装？
    duration: ""           # 大概多久？
    tools_needed: []       # 需要什么工具？
    body_posture: ""       # 安装姿势（举过头顶/蹲下/梯子上）
    actions: []            # 物理动作：举、对准、拧、卡、挂、穿线
    form_constraints: []   # 对造型的约束（如：必须单手可托住、接线区朝向明确）
    
  3_daily_use:
    who: ""                # 谁日常操作？
    frequency: ""          # 操作频率
    duration: ""           # 每次多久？
    actions: []            # 物理动作：按、拧、拨、触摸、遮挡
    form_constraints: []   # 对造型的约束（如：开关位置必须盲操可达）
    
  4_adjust:
    who: ""                # 谁调节？
    scenarios: []          # 什么情况下调节？（角度/亮度/高度/方向）
    actions: []            # 物理动作：扭、推、滑、旋
    form_constraints: []   # 对造型的约束（如：旋转关节必须外露且有阻尼感）
    
  5_maintain:
    who: ""                # 谁维护？
    frequency: ""          # 多久一次？
    tools_needed: []       # 需要什么工具？
    actions: []            # 物理动作：擦、拆、换、清
    form_constraints: []   # 对造型的约束（如：灯罩必须免工具可拆）
    
  6_troubleshoot:
    worst_case: ""         # 最容易出错的操作是什么？
    recovery: ""           # 出错了怎么恢复？
    actions: []            # 物理动作
    form_constraints: []   # 对造型的约束（如：接线端子必须可视化确认状态）
```

### 物理交互汇总

从6阶段中提取所有物理交互（grip / press / twist / lift / hang / slide / snap / wipe），汇总为该方向的**造型约束清单**：

```yaml
form_factor_constraints:
  strategy_id: "S-01"
  must_have:     []  # 造型必须满足的物理交互需求
  nice_to_have:  []  # 满足后体验更好
  conflicts:     []  # 不同阶段的需求冲突（如：安装要轻 vs 使用要稳）
```

**此清单作为硬输入传递给 Step 05，概念生成时必须逐条回应。**
