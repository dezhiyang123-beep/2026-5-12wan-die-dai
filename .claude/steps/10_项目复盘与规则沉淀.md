# Step 10：项目复盘与规则沉淀

## 目标
项目交付后（或中途终止后），系统自动复盘，将经验沉淀为客户记忆和系统规则改进。

**没有复盘，系统不会进化。** 这一步是系统从"能用"到"越来越好用"的关键。

## 触发条件
- Step 09 交付包装完成后自动触发
- 或用户主动说"复盘" / "项目结束"

## 执行

### 第一步：客观指标记录

系统自动统计，不需要用户输入：

```yaml
project_metrics:
  client: ""
  category: ""
  date: ""
  mode: "fast/standard/deep"
  
  # 自动统计
  total_concepts_generated: 16
  concepts_survived_review: 8
  concepts_user_selected: 6
  concepts_passed_pugh: 5
  avg_render_iterations: 0    # 每概念平均出了几轮图
  steps_redone: []            # 哪些步骤被用户要求重做
  
  # 新增：结构化经验记录
  failures: []           # 被否概念的失败因素（自动从Step 05/06收集）
  successes: []          # 被选概念的成功因素
  
  # 用户后续填入
  concepts_accepted_by_client: null  # 客户选了几个（客户反馈后补）
  client_rejection_reasons: []       # 被否的原因
```

记录到 `.claude/project_log.yaml`。

### 第二步：极简复盘（5个选择题，不写长报告）

**复盘必须轻量，否则用户不会执行。** 只问5个选择题：

```
Q1. 客户选了几个方案？
  A. 0个  B. 1-2个  C. 3-4个  D. 5个  E. 还没给客户看

Q2. 被否掉的方案主要因为什么？
  A. 不像品牌  B. 造型不够好  C. 成本超了  D. 制造做不了  E. 不回应需求  F. 没被否

Q3. 渲染图和概念一致吗？
  A. 非常一致  B. 基本一致，小调整  C. 偏差明显，多轮迭代  D. 严重漂移

Q4. 本项目中最大的问题出在哪一步？
  A. 需求/方向(03)  B. 灵感/迁移(04)  C. 概念质量(05)  D. 渲染(08)  E. 没有明显问题

Q5. 本项目的经验应该：
  A. 存进这个客户的记忆  B. 存进品类规则  C. 改通用规则  D. 加入反例库  E. 不需要存
```

### 第三步：结构化经验提炼（系统自动执行，不需要用户输入）

基于Q1-Q5的回答和项目过程数据，系统自动提炼：

**被选中概念的成功因素**：
```yaml
successes:
  - concept_id: ""
    why_selected: ""           # 客户为什么选这个
    key_technique: ""          # 用了什么设计手法（H01-H12）
    key_reference: ""          # 灵感来自哪张参考图
    reusable_insight: ""       # 可复用的设计洞察
```

**被否决概念的失败因素**（从Step 05/06已即时记录的反例中汇总）：
```yaml
failures:
  - concept_id: ""
    failure_type: ""           # 品牌不符/造型弱/成本超/制造不可行/不回应需求
    root_cause: ""             # 根因
    rule_generated: ""         # 生成的规则
    rule_scope: "client"       # client/category/universal
    valid_until: "permanent"   # permanent / 具体日期 / needs_recheck
```

**存储位置**：
- rule_scope=client → 写入 `.claude/clients/{客户名}/project_history.yaml`
- rule_scope=category → 写入 `.claude/knowledge/反例库/` 对应品类文件
- rule_scope=universal → 写入 `.claude/knowledge/反例库/通用反例_种子库.yaml`

### 第四步：系统自动处理（根据选择题结果）

系统根据Q1-Q5自动执行：
- Q1选A/B → 标记低命中项目，分析Q2原因
- Q2选A → 检查品牌语法是否需要更新
- Q3选C/D → 检查Step 08参考图是否需要更换
- Q4指向哪步 → 该步骤的反馈进入对应规则库
- Q5决定存储位置

**不需要用户写任何文字。** 系统根据选择自动分类和处理。

如果需要更细的反馈（如具体哪个概念被否、为什么），系统追问1-2个选择题，不超过3分钟。

### 第四步：反馈分类确认（仅在Q5选B/C时触发）

系统列出本项目关键反馈，给选择题确认：

```
反馈："方向太保守"
系统建议分类：品类规则

请确认：
A. 这是这个客户的特殊偏好 → 存客户记忆
B. 这是该品类的通用问题 → 存品类规则（出现2次即沉淀）
C. 这是所有项目的通用问题 → 存通用规则候选（需≥3客户确认）
D. 这是致命问题 → 立刻加入红线
```

### 第五步：客户记忆更新

将本项目的经验写入客户记忆文件：

```yaml
# .claude/clients/{客户名}/project_history.yaml 追加一条
- project_date: "2026-04-26"
  category: "电钻"
  concepts_delivered: 5
  concepts_accepted: null
  key_learnings:
    - "客户喜欢有力量感的设计，不喜欢过于精致"
    - "品牌距离4分的概念最受欢迎"
  brand_grammar_updates:
    - "确认：黄色只用于功能分区，不做整面黄"
  preferences_updates:
    - "偏好激进方向比保守多"
  failures:
    - concept_id: ""
      failure_type: ""           # 品牌不符/造型弱/成本超/制造不可行/不回应需求
      root_cause: ""             # 根因
      rule_generated: ""         # 生成的规则
      rule_scope: "client"       # client/category/universal
      valid_until: "permanent"   # permanent / 具体日期 / needs_recheck
  successes:
    - concept_id: ""
      why_selected: ""           # 客户为什么选这个
      key_technique: ""          # 用了什么设计手法（H01-H12）
      key_reference: ""          # 灵感来自哪张参考图
      reusable_insight: ""       # 可复用的设计洞察
```

**brand_grammar.yaml 和 preferences.yaml 更新规则（防覆盖）**：
- 不覆盖旧版本。在文件头部追加新版本块，保留所有历史版本。
- 每个版本块标注：版本号、日期、项目ID、更新原因。
- `brand_grammar_updates` 和 `preferences_updates` 中列出的变更，作为新版本块的增量内容追加到对应文件。
- 系统读取时取最上面（最新）的版本块。
- 具体格式见 Step 03 的"客户记忆写入规则（防覆盖）"。

### 第六步：失败案例入库

如果有被否掉的概念，将否决原因存入反例库：

```yaml
# .claude/knowledge/反例库/ 追加
- anti_id: "ANTI-{项目编号}-01"
  source: "本项目概念C-07"
  what_not_to_do: "用消费电子的圆润过渡做电动工具握把"
  why_dangerous: "看起来不够强悍，不像专业工具"
  applies_to: "电动工具品类 / 工业风格品牌"
```

### 第七步：规则变更检查

系统自动检查：
1. 本项目的反馈中，有没有标记为"通用规则候选"的？
2. 检查记忆库中，这条反馈是否已在 **≥3个不同客户** 或 **同品类≥2次** 出现？
3. 如果达到阈值 → 提出具体的规则修改建议

```yaml
rule_change_proposal:
  what: "Step 05 品类假设挑战概念从2个改为3个"
  why: "Agrolux、RAB、本项目都反馈安全概念太多、缺少突破性"
  from_projects: ["agrolux_202604", "rab_202605", "dewalt_202604"]
  expected_improvement: "边界款质量提升"
  review_after: "2个项目后复查"
```

用户批准 → 系统修改规则文件 + git commit（附变更日志）。

### 第八步：素材库扩充

本项目中发现的优质参照和新品类图片，建议入库：

```
本项目可入库的素材：
  - DeWalt DCD999 产品图 × 3 → 品类标杆库 + 品牌语法库
  - Milwaukee M18 产品图 × 2 → 品类标杆库
  - 本项目渲染成功的概念图 × 2 → 品牌语法库（作为"我们为该品牌做的设计"）
```

## 输出

```yaml
project_debrief:
  metrics: {自动统计的指标}
  feedback_classified: {分类后的反馈}
  client_memory_updated: true/false
  anti_examples_added: 0
  rule_changes_proposed: 0
  assets_suggested_for_library: []
```

### 产出完整性自检
- [ ] 客观指标已记录
- [ ] 5选择题复盘已完成
- [ ] 结构化经验提炼已完成（failures+successes）
- [ ] 客户记忆已更新（遵守防覆盖规则）
- [ ] 失败案例已入反例库
- [ ] 规则变更检查已执行（达到阈值的已提出提案）
- [ ] 素材库扩充建议已输出

**git commit 本项目所有变更（客户记忆+反例库+指标）。**
